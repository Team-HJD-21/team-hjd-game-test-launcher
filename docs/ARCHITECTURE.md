# TeamHJD Game Test Launcher

## Scope and technology

Windows 10/11 x64 and macOS15+ Apple Silicon/Intel, C++20, Qt6.11.3 Quick/Controls, CMake/Ninja with MSVC or Apple Clang. Qt is dynamically linked. The public repository contains the launcher, bounded Python distribution/device-authentication server, operator scripts, synthetic tests and supplied logos. Game builds, signing keys, credentials and user logs stay in private storage. Unity source is outside this project and is never built or modified here. See the [release runbook](RELEASING.ko.md) and [known failures](TROUBLESHOOTING.ko.md) before maintenance. Device authentication below describes0.2.3; production activation and current public version are recorded separately.

The Qt installation is supplied through an explicit SDK path; no paths to another project are embedded in the executable. Current public hosting uses Cloudflare Access/Tunnel to a loopback origin without opening the origin port to the Internet. Per-user logon startup and recovery are explicit operator configuration, separate from installing a launcher.

## Private game update

1. The default channel pins the production HTTPS URL and P-256 publisher key. Cloudflare Access verifies the browser's email One-time PIN. After explicit privacy consent, the origin independently verifies the edge's JWT signature, exact issuer/audience and email before enrolling a device public key. The device private key is encrypted with Windows current-user DPAPI or Mac Keychain-backed encrypt-then-MAC; it is never sent to the server, placed in URLs or logged. Google login is not used. Separate trusted invite/password channels remain supported.
2. Device catalog/package requests use `/client-device/` and a60-second single-use challenge signed over method, exact path, Range, client version and consent version. This exact Access subpath delegates authentication to the origin; initial enrollment remains under the original email Access application. Registry corruption is503, expired nonce409 with one retry, revoked/unknown keys401 with reauthentication. Public GitHub transport receives no device/email credentials. Operator revocation, self-logout, email deletion and180-day inactivity stop new requests; existing files are not remotely deleted. Legacy clients retain the original authenticated `/catalog.json` path during staged rollout. Legacy password credentials remain base64-encoded UTF-8 **over TLS**; encoding is not encryption. Private redirects are rejected. See [Cloudflare configuration](CLOUDFLARE_ACCESS.ko.md) and [device protocol](DEVICE_LOGIN_PLAN.ko.md).
3. The envelope carries the exact signed payload bytes in base64 and an ECDSA P-256/SHA-256 signature in IEEE P1363 format. Windows CNG or Apple Security verifies against the pinned publisher key before parsing game records. The payload includes schema, monotonic sequence, issued/expiry timestamps (seven days by default; maximum eight), per-game archive SHA-256/size, full runtime file SHA-256/sizes and executable. Schema 1 retains its Windows record and adds Mac variants under `platforms`; native clients choose an exact CPU match or a universal Mac package. Windows 0.1.2 ignores the nested variants and retains its original record.
4. Download to a hash-specific `.part`, with bounded streaming, timeout and validated byte ranges. Interrupted data remains for retry. A full SHA-256 comparison is mandatory after resumed downloads. A changed hash uses a different partial file.
5. Parse and preflight the whole ZIP before extraction. Reject unsafe Windows paths, absolute paths, traversal, ADS, device names, trailing dots/spaces, case-fold collisions, directory/file collisions, links, encryption, unsupported compression, too many files and excessive sizes/ratio. Require exact signed file coverage, size and digest. Never invoke an archive command supplied by a server.
6. Extract to a uniquely named version directory on the same filesystem. The receipt is written only after all files pass. `QSaveFile` replaces `active.json` atomically, recording current and previous versions. Incomplete directories are inert; they are preserved for diagnosis and never activated. Current files are never overwritten.
7. Verify installed files before launching via an absolute executable path with an empty argument list. Track PID, executable path and process creation timestamp, including after a launcher restart. Installation and rollback are blocked while that game runs. A per-game lock serializes activation and launch. Save data stays in the game's AppData/LocalLow location.

Identical verified archive/version/file manifests are a no-op, so an already installed package is not installed twice. Explicit repair creates a new verified replacement. Rollback verifies the previous tree and switches the pointer. The newer release remains available through the explicit Update action; it is never automatically reapplied. Old versions remain available until game deletion. Uninstall blocks a running game, preflights links, renames only the managed version tree to a scoped removal directory, clears active state and removes that tree. A durable marker permits a failed deletion to resume. External AppData saves and playtest logs remain untouched; known archive cache files are removed. The app does not upload logs.

## Public launcher update

The stable Windows `TeamHJDLauncher.exe` boots `launcher/versions/<version>/TeamHJDClient.exe`. The payload holds Qt DLLs and QML dependencies, allowing client and dependency updates without replacing loaded files. On Mac, `TeamHJDLauncher.app` in Applications seeds and launches managed `TeamHJDClient.app` versions in architecture-specific Application Support storage. Validated updates also manage the stable app through a seed-free bootstrap bundle. The payload asset name is fixed separately for Windows x64, macOS arm64 and macOS x64.

The client compares P-256 signed static feeds from the download site and the official GitHub Release asset without a PAT or email credentials. It enforces the pinned publisher key, monotonic sequence, expiry, platform and exact official asset URLs/size/hash, rejecting equal-sequence conflicts. Checks run about once a minute, with bounded error backoff. Public redirects are limited to HTTPS GitHub asset hosts. A checksum alone is not proof of authenticity.

An available update requires explicit approval before download, independently of email login. It displays a separate progress flow, verifies all files and restarts automatically. Windows installed clients hand off to the checked Setup so the stable executable, shortcuts, uninstaller and Installed Apps version stay consistent. Portable clients use a checked payload/bootstrap transaction. The bootstrap waits for the exact old client, writes durable pending state and requires a fresh health acknowledgment after a rendered frame. Mac credentials are restored after acknowledgment so Keychain approval does not cause false rollback. Failed activation restores the previous verified version and suppresses repeated activation of that failed release. Only a newly created unresponsive client child may be terminated; games and unrelated processes are never terminated.

Catalog checks run on startup, selection and app reactivation, every two minutes while connected and every thirty seconds while offline. Automatic checks only announce game updates; download starts from the user's Update action. A running game blocks installation. Game launch requires online catalog access and verified launcher metadata; offline bypass is unavailable. After the first successful launcher check, routine checks use the footer's animated dots and keep the UI available; a real new launcher or connection failure still blocks as required. Notifications record meaningful connection/install/restore changes.

## Storage

- Portable installation: bootstrap/dependencies, `launcher/active.json`, immutable `launcher/versions/` and transient health/pending records.
- `%LOCALAPPDATA%/TeamHJD/Launcher/`: settings with DPAPI blob, signed catalog cache, downloads, default games. `--data-root` creates isolated test profiles.
- Mac `~/Library/Application Support/TeamHJD/Launcher/`: encrypted settings, catalog cache/downloads and `games/`; managed launcher versions are in sibling `LauncherRuntime-macos-arm64/` or `LauncherRuntime-macos-x64/`.
- Per game: `games/<id>/active.json`, `running.json`, `versions/<version-hash-random>/` and receipt.
- Operator: publishing tools default to `.local/private-distribution/`, hosting tools to `.local/production-distribution/`; pass the intended `-PrivateRoot` explicitly. It contains publisher DPAPI key, password verifier, invite, catalog, private ZIPs and verified-user audit. HTTP exposes authenticated catalog and hash-named ZIP API routes. The former manual game-download HTML routes (`/`, `/downloads`) are retired: authenticated requests receive empty HTTP410, with no link or redirect; queries still receive HTTP404. The existing Access application, launcher login, audit and package Range handling remain in place. The local operator dashboard and verified-email reports are not public routes. Public launcher ZIP distribution is separate; see [public distribution](PUBLIC_DOWNLOADS.ko.md).

## Trust and limits

The threat model covers hostile/corrupt network responses, malformed archives, replayed device proofs, interruption, stale signed catalogs, concurrent app copies, game process locks and failed client activation. A malicious local process running as the same OS user can alter both executable and local receipt; this is not a local malware sandbox. Package authenticity comes from the signed catalog and launcher updates from the pinned signed feed plus valid TLS. Windows binaries use CFG, ASLR, high-entropy VA, DEP, stack protection and app/system-only import resolution, checked against the actual PE. These flags do not secure every dynamic load or a compromised OS. Authenticode signing, Apple Developer ID and notarization are not configured; first-download publisher identity and platform reputation are not claimed. Ad hoc Mac signature checks do not substitute for notarization or actual Unity gameplay testing.

Certificate validation remains enabled. Private CA trust is request-local and provided by the invite; no global root store is modified and no TLS error is ignored. Changing publisher keys or CA certificates requires a new invite over the trusted team channel. Back up the publisher key safely; DPAPI keys are tied to this Windows account/machine. A missing signing key is not recovered by trusting a new unauthenticated key from the distribution server.
